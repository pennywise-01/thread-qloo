# Taste
- Prefers short, focused answers: when he asks for a specific deliverable (e.g. "title with brief description only"), he wants just that and nothing more — trims long multi-section responses down to the essentials. Default to tightening output rather than expanding it. Confidence: 0.65
- Wants scaffolding and a running MVP first — built against mocked/stubbed layers when live API credentials aren't available yet — then validate on a small test case before wiring up the real API. Deliver a runnable skeleton early instead of waiting for keys or a full implementation. Confidence: 0.7
- After a mocked build lands, he audits it from the end user's / judge's standpoint: "what does this actually help with?" Push-back lands when the demo contains invented content (fictional venues, dropdown quizzes) or value expressed only as uncalibrated numbers. Expects the next step to replace placeholders with real data and to show a tangible consequence a person would feel. Confidence: 0.6
- Optimizes for what a judge/evaluator will directly see and feel: prefers investing the next pass in the demo surface (real entities he can type, participation paths like "put yourself in the group", human-readable outcomes instead of raw scores) over further engine internals. A terse "make it so they take notice" means "spend the effort on visible demo impact." Confidence: 0.6
- Treats platform/API rules as binding requirements, not suggestions: credentials stay server-side (never in a browser bundle or committed), no personal data (names, emails, device ids) is sent to third-party APIs, and the live integration must use the vendor's officially supported surfaces. When he forwards a spec or setup guide, he expects the implementation to conform to it rather than assume. Confidence: 0.65
- Wants the live-credential switch to be a drop-in configuration change (a single mode flag / adapter seam) so the mocked build carries over untouched when the real key arrives. Confidence: 0.55
- Expects the vendor API to be the thing that *decides* — "the determination is coming from qloo api" — with local scoring treated only as a temporary stand-in that gets deleted when the key lands, not as the product's logic. State plainly which step the API replaces. Confidence: 0.6
- Specifies the input surface concretely: real user controls (a labelled multi-select grid for preferences, segmented controls for budget) rather than a scripted preset demo or free-form chat. "Accept from user input" means the user supplies days + likes themselves, and the UI shape should be named back to him before building. Confidence: 0.55
- Objects to arbitrary hard-coded caps on a user-owned quantity — "instead of limiting to only 4 days, make it user input" — and reaches for realistic real-world values ("they can put like 2 weeks"). When a range is short and discrete, he treats it as an unfinished thought rather than a design decision: expose a free-form numeric input (with sensible bounds and quick presets), and make the underlying logic actually handle the larger range instead of just widening the control. Confidence: 0.6
- Wants the product explained in plain language *before* more building — "explain to me first", "I really don't understand anything". When he says this, more architecture detail (pipeline stages, engine internals, score mechanics) makes it worse; the fix is a concrete user-facing before/after (what a normal approach picks vs. what this picks, and who pays) plus a plain statement of the weak spots. Confidence: 0.7
- When he asks "what is it actually calculating?", he wants the single quantity named plainly and traced on a worked example with the real numbers (one person's signals → a score, then the step that produces the final answer) — not a tour of pipeline stages or code structure. Confidence: 0.55
- Judges the product by whether a person can act on its output: wants a concrete deliverable (a fixture for this room, this dish tonight, this next step) rather than an optimization metric. "What will these numbers show and tell? how do people understand this?" is a demand to make the output human-usable, not to explain the math better. Confidence: 0.75
- Wants the product built around a hard, real constraint that generic advice violates (easy-to-chew / low-heat / medication-aware food, budget, no car, mobility) with taste layered on to make it personal. A decision where nobody is blocked (friends picking a bar) reads as a toy no matter how correct the engine is. Note: he also pitches purely taste-led scenarios himself (e.g. a Tokyo trip from indie rock / specialty coffee / vintage), so treat the constraint as strongly preferred rather than mandatory. Confidence: 0.6
- Measures an idea against what a generic LLM would already answer: the value pitch must be data-driven personalization + local relevance that a plain model would get generic or hallucinate. If "I asked ChatGPT and got the same list" is a plausible judge rebuttal, the idea needs a mechanical differentiator (real scoring across the whole candidate pool, route/schedule feasibility, or an explicit skipped-and-why list). Confidence: 0.6
- Pitches product ideas as a first-person user scenario — "a user says: *I'm visiting Tokyo next week, I love X, Y, Z, what should I check out?*" — then states what the agent should do better than a standard LLM. Match that shape when proposing or critiquing directions: concrete scenario first, mechanism second. Confidence: 0.5
- Once he approves a direction or hands over a resource ("yes do it", "do what you want with it"), he grants broad autonomy: he expects the remaining implementation and design calls to be made and carried through end to end, then reported, rather than paused on for option menus or per-step permission. Confidence: 0.5

When a feature becomes multi-city/multi-locale, keep labels and glyphs universal — and apply the same generic mark *everywhere* that quantity is shown (results, metadata, CLI output), not just in the control he originally flagged; a leftover `¥` anywhere means one shared component, not per-file one-offs. Confidence: 0.75
- Dislikes filler copy in controls: a hint that only restates a non-action ("do not filter by price" on the *Any* tier) is "unnecessary" — better to render nothing than text that carries no information. Confidence: 0.5
- Before committing to a feature that depends on third-party data, asks for a feasibility/complexity assessment of the real API first — "assess first how complex and if the API can do it or not" — and expects the answer to be backed by actual probe calls across a spread of cases plus an honest list of what breaks in the current code, with the open design decisions named and confirmed before building. Confidence: 0.55
- Rejects subtle, low-contrast UI marks: tiny icons at reduced opacity read as "transparent, can't really see it" and get sent back — and he will repeat the complaint, narrowing it to specific surfaces ("in the populated results"), if the first fix left any instance still faint. When rendering small indicators/glyphs, size and contrast them to be immediately legible rather than de-emphasizing them for visual polish. Confidence: 0.65
- Willing to abandon a working, verified build outright once the use case fails to show value ("I don't see any value in what you built") — prefers pivoting the problem/domain over further polishing the existing solution. Don't defend the artifact; re-pick the problem. Confidence: 0.65
